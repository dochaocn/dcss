# 撰写可执行 Plan

## 动手前（必做）

1. **先讨论、后写文档**：业务规则未确认时，用提问补齐（维度、边界、删留字段、前后端谁改），不要静默选型。
2. **先查代码、后写方案**：`grep` / GitNexus 摸清现状——字段读写点、调用链、前端页面、已有类似实现；plan 中的文件路径必须来自仓库实况。
3. **确认输出路径**：默认 `docs/{主题}.md`（英文 snake_case 文件名）；用户指定路径时从其指定。
4. **确认范围**：写清涉及仓库（如server / admin / merchant）与非目标。

## 文档质量标准

| 原则 | 说明 |
|------|------|
| **可执行** | 他人按文档能分步实施，不依赖口头补充 |
| **可验收** | 期望章节用 `- [ ]` 勾选清单，可逐条验证 |
| **可回滚** | 分 Phase，每步可独立上线/回滚 |
| **重回归** | 单独测试章节；强调「一致或更准」，避免未知 bug |
| **最小惊扰** | 优先停写→改读→删字段；不大爆炸式重构 |
| **索引完整** | 列出改动文件清单，按仓库/类型分组 |

语言：本项目 plan **正文用简体中文**；代码、路径、字段名保持英文。

## 分 Phase 策略（默认模式）

```
Phase 0  准备：评审文档、测试数据、改造前基线
Phase 1  止血：低风险、可立即减轻错误（如停写脏字段、去掉误导性 UI）
Phase 2  核心：统一服务、改造主链路、列表/筛选/enrich
Phase 3  清理：删字段、删废弃 API、DB 迁移（单独脚本、低峰执行）
```

- **删库表字段**必须放在最后一 Phase，且前面 Phase 已验证「不读不写」该字段。
- 每个 Phase 写明「验收」与「回滚方式」。

## 测试章节必写内容

1. **业务回归**：列出所有受影响的**端到端链路**（不只测改动的函数）。
2. **边界用例**：多租户、多通道、中间态、并发、历史数据（若适用）。
3. **发版前 grep**：给出可复制的 `rg` 命令，检查遗漏引用。
4. **灰度**：索引/性能/对外 API 兼容等风险与缓解。
5. **删列门槛**：全量测试 + 生产观察周期（若适用）。

## 与编码规范的关系

- Plan 阶段**不写实现代码**（除非用户同时要求）。
- Plan 中的实现步骤应能与 `karpathy-guidelines` 对齐：每步改动可追溯至需求条目。
- Plan 中显式写**归属字段**（如 xId、yId）传递链。


## 产出检查（写完自检）

|  |  |
|---|------|
| 1 | 需求边界与非目标是否写清？ |
| 2 | 期望是否可勾选验收？ |
| 3 | 实现是否基于真实代码路径？ |
| 4 | 步骤是否分 Phase、可回滚？ |
| 5 | 回归是否覆盖全部受影响链路？ |
| 6 | 是否有 grep/发版前检查？ |
| 7 | 文件索引是否完整？ |

全部 Yes 后交付用户；若有 No，先补文档再回复。

## 用户仅说「写 plan」时的默认流程

1. 读取本 skill
2. 若上下文不足：先 1–3 个关键澄清问题（或引用已讨论结论）
3. 搜索代码验证假设
4. 写入 `docs/{topic}.md`
5. 回复用户：文档路径 + 章节摘要 + 建议从哪一 Phase 开工
