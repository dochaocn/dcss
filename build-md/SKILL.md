# 项目 README 撰写（build-md）

## 何时使用

用户需要**新建或重写**仓库根目录 `README.md`（或明确要求的项目说明文档）时启用；目标是让读者能快速理解**做什么、怎么跑、接口/页面如何组织**。

## 前置动作（必须）

1. **识别项目类型**：浏览 `package.json`、`go.mod`、`pyproject.toml`、`pom.xml`、`Cargo.toml`、目录名（如 `apps/web`、`server`）等，判断偏**前端**、**后端**还是**混合/工具库/其他**。
2. **以代码为准**：路由、页面、接口路径、环境变量、启动命令须从**实际配置与源码**提取；不得臆造不存在的 API 或脚本。
3. **缺失信息**：若仓库未实现某块（如无路由文件），在 README 中如实写「未配置」或省略该小节，并可在「待完善」中一笔带过。

## README 通用约定

- **语言**：与用户对话语言一致；本技能默认用户要求中文时使用简体中文。
- **标题层级**：从 `# 项目名称` 起，主要章节用 `##`。
- **链接**：外部文档、设计稿、监控地址等用完整 URL；内部可链到 `docs/` 下文件（若存在）。
- **命令**：给出可复制的一行命令；区分开发环境与生产环境时分开写。

## 前端项目（必选结构）

按下列顺序组织；无某一项则删节或标注「无 / 待补充」。

### 1. 项目简介

一两句话：产品定位、主要用户或场景。

### 2. 页面与功能

用表格或列表说明**主要页面/视图**及其**核心功能**（用户能做什么）。

| 页面/模块 | 功能说明 |
|-----------|----------|
| … | … |

### 3. 路由

列出**路由路径 → 页面/组件**对应关系；若使用文件式路由（如 Next.js App Router），说明约定并列出重要路径。

示例格式：

```text
/              → 首页
/login         → 登录页
/dashboard     → 仪表盘
```

### 4. 每页接口大纲

按**页面或路由**分组，列出调用的**接口方法 + 路径（或封装函数名）+ 一句话用途**。若前端仅通过 BFF/聚合层，写清调用链（页面 → SDK 方法 → 后端路径）。

示例：

```text
登录页
- POST /api/auth/login — 提交凭证
- GET /api/auth/me — 登录后拉取用户信息
```

### 5. 技术栈（简述）

框架、构建工具、UI 库、状态管理等一行列出即可。

### 6. 本地启动

- 环境要求（Node 版本、包管理器等）
- 安装依赖命令
- 环境变量：列出**变量名**与含义（可复制 `.env.example` 说明）
- 开发启动命令
- 构建与预览（若有）

### 7. 部署

- 产物目录（如 `dist/`、`out/`）
- 静态托管或容器化要点（若有 Dockerfile / CI 则与文件一致）
- 生产环境变量与注意事项

### 8. 其他（按需）

测试命令、代码规范、目录结构简图、相关文档链接等。

## 后端项目（必选结构）

### 1. 项目简介

服务职责、边界（不负责什么若需说明可写）。

### 2. 仓库结构

用树形或表格说明**顶层目录**职责，例如：`cmd/`、`internal/`、`api/`、`pkg/`、`configs/`、`scripts/`、`deploy/`。与仓库实际一致。

### 3. 技术架构

- **运行时与框架**（语言版本、Web 框架、ORM 等）
- **核心依赖**（消息队列、缓存、数据库客户端等）
- **分层或模块划分**（如 handler → service → repository），可用简短列表或示意图（mermaid 可选，保持精简）

### 4. 接口概览

- 若有 OpenAPI/Swagger：写生成方式与访问 URL 或文件路径。
- 否则按**模块或资源**列出 REST/RPC 路径与方法，或说明「详见 `xxx` 路由注册处」并列出主要分组。
- 认证方式（JWT、API Key、Session）与全局前缀（如 `/api/v1`）。

### 5. 本地启动

- 依赖服务（数据库、Redis 等）与**最低版本**
- 配置方式（配置文件路径、环境变量表）
- 数据库迁移/种子命令（若有）
- 启动命令与健康检查路径（如 `GET /health`）

### 6. 部署

- 构建产物或镜像构建方式
- 端口、进程管理、环境变量清单
- 与 `Dockerfile`、K8s、`docker-compose` 或 CI 一致，不重复编造步骤

### 7. 未来 Feature / Roadmap

用列表写出**已讨论或计划中的能力**；若仓库无 issue/文档依据，标注「规划待确认」或仅写技术债与已知限制。

### 8. 其他（按需）

错误码约定、日志与监控、贡献指南、安全披露等。

## 混合仓库（前后端同仓）

可拆成两个子章节：**前端 README 要点**与**后端 README 要点**，或根 README 用链接分别指向 `apps/web/README.md`、`services/api/README.md`（若用户希望只维护根 README，则在根文档分节写全）。

---

## 其他类型（CLI、库、单脚本）

在「简介 + 安装 + 使用 + 配置 + 开发/发布」基础上，按性质补充：

- **CLI**：子命令一览、全局选项、退出码。
- **库**：导出 API 摘要、peer 依赖、最低运行时版本。
- **Monorepo**：包列表与各包职责、根目录常用脚本。

## 输出与自检

- 保存路径默认为仓库根目录 `README.md`；用户指定其他路径时从其指定。
- **自检清单**：
  - [ ] 类型判断与章节与仓库匹配
  - [ ] 路由/接口/命令均可在仓库中找到依据
  - [ ] 启动与部署步骤可复现
  - [ ] 前端含：功能、路由、每页接口大纲（若适用）
  - [ ] 后端含：结构、架构、接口概览、部署、未来 feature（若适用）
