# Java Risk Review

## 目标

对 Java 后端项目进行高风险和中风险审查，重点识别：

- 可能导致线上故障的 bug
- 业务逻辑错误
- 业务规则冲突
- 数据一致性问题
- 事务、并发、幂等问题
- 权限、安全、越权风险
- 接口设计不合理
- 可维护性差且可能引发业务问题的设计
- 异常处理、边界条件、状态流转缺陷

只输出高风险和中风险问题。低风险、代码风格、轻微命名问题、无实际业务影响的建议不要列入主清单。

## 审查原则

优先从业务正确性出发，不只做代码静态检查。

审查时必须结合：

- Controller 接口入口
- Service 业务编排
- Mapper/Repository 数据访问
- DTO/VO/BO/Entity 字段含义
- 枚举、状态机、常量
- 数据库唯一性、更新条件、软删除字段
- 事务边界
- 权限和租户隔离
- 外部接口调用
- 定时任务、消息消费、异步任务
- 历史代码调用链

不要因为代码写法“不优雅”就判定为风险。必须说明它如何影响业务、数据或线上稳定性。

## 工作流程

### 1. 建立项目上下文

先阅读项目结构和关键配置：

- `pom.xml` 或 `build.gradle`
- `src/main/java`
- `src/main/resources`
- Spring 配置文件
- MyBatis Mapper XML 或 JPA Repository
- Controller、Service、Job、Consumer 等入口类
- 枚举、常量、状态定义

优先使用 `rg` 搜索以下内容：

- `@RestController`
- `@Controller`
- `@Service`
- `@Transactional`
- `@Scheduled`
- `@KafkaListener`
- `@RabbitListener`
- `@RequestMapping`
- `@PostMapping`
- `@GetMapping`
- `update`
- `delete`
- `status`
- `state`
- `type`
- `tenant`
- `userId`
- `companyId`
- `deleted`
- `isDeleted`
- `lock`
- `amount`
- `point`
- `balance`
- `stock`
- `order`

### 2. 梳理业务链路

对每个重点模块梳理：

- 入口接口或任务是什么
- 核心业务对象是什么
- 状态如何流转
- 数据如何创建、更新、删除
- 是否存在跨表更新
- 是否存在重复提交、重复消费、重复发放
- 是否存在权限、租户、用户边界
- 异常时是否会留下半成功数据

如果项目有需求文档、接口文档、禅道故事、Bug、README 或数据库表结构，优先结合这些资料判断业务冲突。

### 3. 读写链路数据集合一致性检查

- 不只审写链路，也要审前置读链路
- 对“查询可操作对象”的接口，必须验证返回集合能支撑后续写操作
- 看到 filter/convert/adapter 时，必须追溯过滤前的原始 SQL/Repository 条件
- 新增业务维度后，必须同时检查写入和查回是否使用同一套归属模型
- 旧查询条件、旧类型过滤、旧关系表 join 是新增模型改造中的重点风险源
- 配置或创建成功后仍查不到可操作数据，应视为核心流程不可用风险

### 4. 重点风险类型

#### 业务逻辑风险

检查：

- 状态流转是否缺少前置状态校验
- 同一个业务动作是否可能重复执行
- 金额、积分、库存、次数、余额是否可能多扣、多加、漏扣、漏加
- 业务开关、有效期、上下架、启停状态是否被忽略
- 审核、审批、撤销、回滚流程是否不完整
- 删除或禁用后是否仍可被引用
- 查询结果是否包含无权限或已删除数据
- 分页、排序、筛选条件是否影响业务准确性

#### 数据一致性风险

检查：

- 多表更新是否缺少事务
- 事务中是否包含远程调用、异步调用或不可回滚动作
- 更新条件是否过宽
- 删除条件是否过宽
- `updateById` 是否覆盖了不该覆盖的字段
- 批量操作是否部分成功后无补偿
- 唯一性是否只靠代码判断，缺少数据库约束
- 先查后改是否存在并发覆盖
- 乐观锁、悲观锁、唯一索引是否缺失

#### 并发和幂等风险

检查：

- 重复请求是否会重复创建、重复发放、重复扣减
- 消息消费是否有幂等键
- 定时任务是否可能多实例重复执行
- 状态更新是否使用条件更新
- 是否存在典型的 `select -> check -> insert/update` 竞态
- 是否存在缓存与数据库不一致

#### 权限和数据隔离风险

检查：

- 用户 ID、租户 ID、机构 ID、商户 ID 是否从可信上下文获取
- 是否信任前端传入的用户身份、角色、租户字段
- 查询、更新、删除是否都带权限边界
- 管理端接口和用户端接口是否混用
- 导出、详情、批量查询是否绕过权限
- 是否存在水平越权或垂直越权

#### 接口设计风险

检查：

- `GET` 是否用于有副作用操作
- 参数是否缺少必要校验
- 入参对象是否暴露内部字段
- 出参是否泄露敏感字段
- 接口是否允许客户端控制状态、金额、归属人等关键字段
- 是否缺少业务错误码和明确异常
- 是否存在接口语义与实际行为不一致

#### 异常处理风险

检查：

- 捕获异常后是否吞掉错误
- 失败后是否继续返回成功
- 异常是否导致事务无法回滚
- 空值、空集合、非法枚举是否处理
- 外部接口失败是否有重试、补偿或明确失败状态
- 日志是否足够定位业务对象

#### 设计不合理风险

只在设计问题会造成实际业务风险时列出，例如：

- 一个 Service 同时承担多个业务域，导致状态规则互相污染
- 关键业务规则散落在多个入口，容易出现规则不一致
- 枚举值和数据库状态无统一约束
- 同一业务动作有多个实现入口且校验不同
- 复杂业务没有明确状态机或领域边界
- 复用通用方法导致不同业务场景被错误处理

## 风险等级标准

### 高风险

满足任一条件即可判为高风险：

- 可能导致资损、积分/余额/库存错误
- 可能导致越权访问、数据泄露、越权操作
- 可能导致重复发放、重复扣减、重复创建核心业务数据
- 可能导致核心流程不可用
- 可能导致数据永久不一致且难以自动修复
- 线上触发概率较高，且影响核心业务

### 中风险

满足任一条件可判为中风险：

- 在特定边界条件下导致业务结果错误
- 可能导致部分数据不一致，但可人工修复
- 可能导致接口行为与业务预期不一致
- 可能导致非核心流程失败或误判
- 存在明显设计缺陷，后续需求容易引入高风险问题
- 当前影响有限，但业务量、并发或功能扩展后风险会放大

不要输出低风险，除非用户明确要求。

## 输出格式

使用中文输出。必须按风险等级排序，高风险在前，中风险在后。

每个问题使用以下格式：

```markdown
## 风险清单

### 高风险

#### 1. 风险标题

- 风险等级：高
- 位置：`文件路径:行号`
- 涉及业务：说明对应的业务流程或接口
- 问题描述：详细描述代码当前行为
- 业务影响：说明会造成什么业务错误、数据错误或线上事故
- 触发场景：描述用户、系统或并发场景如何触发
- 证据：引用关键代码逻辑，不要大段粘贴
- 修改建议：给出直接可执行的修改方向
- 推荐方案：给出更完整的设计或重构方案
- 验证建议：说明应补充哪些测试或验证用例

### 中风险

#### 1. 风险标题

- 风险等级：中
- 位置：`文件路径:行号`
- 涉及业务：
- 问题描述：
- 业务影响：
- 触发场景：
- 证据：
- 修改建议：
- 推荐方案：
- 验证建议：
```

如果没有发现高风险或中风险，明确说明：

```markdown
未发现明确的高风险或中风险问题。

剩余风险：
- 说明哪些部分因为缺少文档、表结构、运行环境或调用方上下文而无法完全确认
```

## 修改建议要求

建议必须具体，避免只写“加强校验”“优化逻辑”。

优先给出：

- 应在哪一层修改
- 应增加什么条件
- 应使用什么唯一索引、状态条件或事务边界
- 是否需要补偿任务
- 是否需要抽取统一业务规则
- 是否需要新增测试
- 是否需要兼容历史数据

示例：

```markdown
修改建议：
在确认领取奖励前，先根据 `userId + activityId + rewardType` 查询是否已有成功领取记录，并在数据库增加唯一索引。发放动作使用事务包裹，状态更新使用 `where id = ? and status = INIT` 条件更新，避免并发重复领取。

推荐方案：
将领取流程拆成“资格校验 -> 幂等记录创建 -> 发放 -> 状态确认”四步。幂等记录先落库，发放失败时记录失败原因并允许补偿任务重试。
```

## 审查边界

不要做以下事情，除非用户明确要求：

- 不主动修改代码
- 不自动执行测试
- 不输出低风险清单
- 不因为格式、命名、注释问题单独报风险
- 不对没有证据的问题下确定结论
- 不把猜测写成事实

对于无法确认的问题，使用“疑似风险”或“需要确认”，并说明缺少什么证据。

## 与项目规范结合

如果项目存在 `AGENTS.md` 或用户提供编码规范，审查时同时检查高/中风险修改建议是否符合这些规范。

对于 Java Spring 项目，特别注意：

- Controller 类和方法注释规范
- `GET` 参数是否使用 `@RequestParam`
- 是否使用了 `@PathVariable`
- 对外接口 DTO 字段是否有 `@ApiModelProperty`
- 是否删除未使用 import
- 是否保持最小化改动
