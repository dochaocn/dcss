# 未提交变更要点摘要

## 何时使用

用户需要**简洁**了解当前仓库里**尚未提交**的改动时启用本技能；常与撰写提交说明、自检变更范围一起出现。

## 信息来源

优先依据（按实际需要组合）：

- `git status -sb`：改动了哪些路径、是否已暂存
- `git diff`：工作区相对暂存区/上一提交的差异
- `git diff --cached`：已暂存、待提交的差异

若用户只关心某一分支对比或范围，按其指定范围取 diff。

## 输出格式（必须遵守）

1. 使用**阿拉伯数字编号**，形如 `1.xxx`、`2.xxx`、`3.xxx`（数字与正文之间可用英文句点 `.` 或全角点，全篇一致即可）。
2. **默认每条独占一行**，便于核对字数；若用户明确要求「单行输出」，可写为：`1.xxx 2.xxx 3.xxx`（条目之间用空格分隔）。
3. 按**功能/意图**归类，不要逐文件罗列；同类改动合并为一条。
4. **每条要点不超过 10 个汉字**（不含编号与句点）。
5. 无未提交变更时：一句说明即可，如「暂无未提交变更」。

## 行文原则

- **第三人称式摘要**：陈述「做了什么」，不写「我帮你看了」。
- 先抓**用户可见行为或业务含义**，再提重构/重命名等次要项（若篇幅有限可合并）。
- 不展开具体文件路径，除非用户明确要求。

## 示例

**差（过长、逐文件）：**

```
修改了 UserService.java 和 auth.ts，还有三个测试文件。
```

**好（符合格式与字数）：**

```
1.新增登录校验 2.调整路由配置 3.补充单元测试
```

（若第三条字数需压到 10 字内：`3.补测试用例`）

## 提交确认与执行

在**已输出**上述要点摘要之后（若无未提交变更则跳过本段）：

1. **必须询问**：是否要根据上述要点执行 `git commit`（一句即可，例如：「是否需要根据以上要点执行 git commit？」）。
2. **仅当用户明确表示要提交**（如：需要、是、确认、提交、好）时，才执行提交相关命令；用户未确认或表示否时，**不得**执行 `git commit` 或 `git push`。
3. **撰写 commit message**：用**刚才给出的同一条要点列表**原样拼成说明——默认**单行**，条目之间用空格连接，与输出格式一致，例如：`1.新增登录校验 2.调整路由配置 3.补充单元测试`。若用户要求多行 subject/body，再按其要求调整，但仍须基于同一批要点。
4. **暂存区**：
   - 若已有暂存内容（`git diff --cached` 非空）：直接 `git commit -m "<message>"`。
   - 若暂存区为空但工作区有改动：**先说明情况并询问**是否先 `git add`（例如全部或指定路径）；**仅在用户同意后再** `git add` 与 `git commit`，不得在未授权时擅自 `git add -A`。
5. **执行**：在用户确认的前提下，用终端执行 `git commit`（带 `-m`）；不臆造提交内容，message 与已展示的要点一致。

## 自检

- [ ] 编号为 `1. 2. 3.` 形式
- [ ] 每条 ≤10 个汉字
- [ ] 概括功能，非文件清单
- [ ] 基于实际未提交 diff，不臆测
- [ ] 输出要点后已询问是否提交；未获用户确认前未执行 `git commit`
- [ ] 若需先暂存，已征得用户同意再 `git add`
